# Spec · 编辑器 runtime 规范化

记录日期：2026-11-15。状态：已确认，待实施。这是所有新功能的前置阶段；功能规格见 [designer-workflow.md](designer-workflow.md)，排期见 [ROADMAP.md](../../ROADMAP.md)。

术语：Module、Interface、Seam、Adapter、Depth、Locality 按 codebase-design 的定义使用。

## Problem Statement

MineDesign 的两个编辑器 runtime（设计稿、设计系统）来自发布产物的还原代码。维护者现在面对的是一个黑盒：

- 文件之间不使用 import。所有函数挂在一个共享注册表上，再从注册表读取。设计稿 runtime 有 665 个文件、约 7956 处绑定、3787 个跨文件名称。依赖关系从目录和 import 中看不到。
- 静态类型被擦除，约 7 万处使用 `any` 的别名；局部变量是机器生成的名称，约 7.5 万处。
- 画布主文件基本是一个约 2.2 万行的函数。评论、测距、播放、Tweaks 的逻辑都嵌在其中。
- 整个 runtime 只有 1 个测试。修改后是否破坏交互，没有任何自动提示。

实际影响：设计师提出的每一项改进（评论、原型演示、测距、版本、Tweaks、Motion）都要修改这部分代码。在现状下，每次修改的范围不可预测，回归只能靠手动查看。继续在黑盒上叠加功能，维护成本会持续上升。

## Solution

先把 runtime 变成依赖可见、领域清晰、有回归保护的代码，再开发新功能。整个过程保持设计师看到的行为不变。

1. **行为基线**：在浏览器模式下，用脚本驱动两个编辑器完成一组固定场景，记录截图、写回的作品文件、编辑器与外壳之间的消息、控制台错误。之后每一步改动都与基线比较。
2. **依赖地图**：用脚本从注册表导出每个名称的提供者与读取者，得到真实的模块聚类、循环依赖、初始化顺序依赖和不可达代码。目标模块划分依据这份数据决定。
3. **清理不可达代码**：删除产品范围之外且不可达的模块，减少后续迁移量。
4. **注册表改为 import**：按"扩展 → 分批迁移 → 收缩"的顺序，把共享注册表替换为真实的模块导入。完成后注册表不再存在。
5. **领域抽离**：把评论、选择与几何、预览与播放、Tweaks 等领域从巨型函数中抽出，成为有类型 interface 和测试的 deep module。
6. **巨型函数收尾**：画布主函数只保留视口、画板编排与事件分发；其余大文件按同一方法处理。
7. **设计系统 runtime**：使用同一套工具和流程完成同样的迁移。

## User Stories

1. 作为维护者，我希望从 import 就能看到一个文件依赖什么，以便判断一次修改的影响范围。
2. 作为维护者，我希望目录划分对应真实依赖，以便按领域定位代码。
3. 作为维护者，我希望每个领域模块有类型化的 interface，以便调用方不需要阅读实现。
4. 作为维护者，我希望在 interface 上有测试，以便修改实现时得到即时反馈。
5. 作为维护者，我希望一条命令就能运行全部基线场景，以便每次改动后确认行为一致。
6. 作为维护者，我希望基线失败时能看到具体场景、截图差异和文件差异，以便快速定位原因。
7. 作为维护者，我希望基线在本机浏览器模式下运行，以便不依赖 Codex 或 Claude 宿主。
8. 作为维护者，我希望基线使用独立夹具，以便不改动示例作品和用户作品。
9. 作为维护者，我希望有一份可重复生成的依赖地图，以便用数据决定 seam 的位置。
10. 作为维护者，我希望知道哪些绑定依赖初始化顺序，以便把高风险迁移排在后面。
11. 作为维护者，我希望不可达代码先被删除，以便不为无用代码付出迁移成本。
12. 作为维护者，我希望迁移分批进行且每批都通过基线，以便出现回归时范围很小。
13. 作为维护者，我希望迁移期间主分支始终可构建、可运行，以便功能修复不被阻塞。
14. 作为维护者，我希望注册表最终被完全移除，以便不存在两套依赖机制。
15. 作为维护者，我希望评论逻辑集中在一个模块，以便后续修改评论体验时只动这一处。
16. 作为维护者，我希望选择与元素几何有独立的 interface，以便测距、评论卡片等叠层功能复用。
17. 作为维护者，我希望预览与播放有独立的 interface，以便调整原型演示方式。
18. 作为维护者，我希望 Tweaks 与组件属性有独立的 interface，以便扩展方案选择和动效调节。
19. 作为维护者，我希望画布主函数只负责编排，以便新增叠层功能不需要修改它。
20. 作为维护者，我希望依赖规则由测试检查，以便后续改动不会让依赖重新变乱。
21. 作为维护者，我希望设计系统 runtime 采用同一方法，以便两个编辑器的维护方式一致。
22. 作为使用 Agent 开发的维护者，我希望代码索引能正确解析依赖，以便 Agent 用更少的上下文完成修改。
23. 作为设计师，我希望规范化期间和之后，画布、编辑、播放、评论、保存、导出的表现与之前一致，以便不需要重新学习或重新检查作品。
24. 作为设计师，我希望已有作品不需要任何迁移即可打开，以便规范化对我不可见。
25. 作为维护者，我希望架构文档在每个阶段完成后更新，以便文档与代码一致。

## Implementation Decisions

**顺序与门槛**

- 本阶段先于所有新功能。功能 ticket 以本阶段中对应的领域 ticket 为前置。
- 每个 ticket 的合并条件：构建成功、已有测试通过、基线全部场景无差异。出现差异时修复代码，不更新基线；只有确认原行为是缺陷时才更新基线，并在提交说明中写明。
- 文件格式、文件路由、宿主能力名、编辑器消息、用户文案、样式保持不变。

**行为基线**

- 运行方式：本机 HTTP 服务加浏览器模式，由浏览器自动化脚本驱动。不通过 Codex 或 Claude 的插件嵌入方式。宿主特有的行为（发送到聊天、下载许可）不属于基线，继续单独验收。
- 每次运行把夹具复制到临时工作区，使用固定视口、固定缩放、固定语言与主题，关闭动画与光标闪烁造成的差异。
- 每个场景记录四类证据：关键步骤的截图；场景结束后工作区内作品文件的内容；编辑器与外壳之间的消息序列（归一化授权凭据与来源地址）；控制台错误与未处理异常。
- 比较顺序：文件内容与消息序列逐字比较；截图按像素比较，允许的差异为零，抗锯齿噪声通过固定环境消除。
- 设计稿场景至少覆盖：打开与首屏、平移缩放与聚焦、分页、画板移动与改尺寸、选中元素与层级定位、修改文字与颜色与尺寸、Tweaks 调节、撤销重做、复制粘贴、在画布播放、全屏播放与退出、元素评论与区域评论、评论定位与删除、画布说明与图形、外部文件变更后的刷新、导出。
- 设计系统场景至少覆盖：打开与章节切换、token 修改与保存、组件预览、文档阅读与编辑、素材浏览、文件列表、评论定位。
- 基线产物（截图与记录）属于过程证据，不入库；场景脚本与夹具入库。

**依赖地图**

- 由脚本静态分析生成：每个注册表名称的提供文件、读取文件、读取发生在安装时还是调用时。
- 产出：文件级依赖图、强连通分量、初始化顺序敏感的名称清单、不可达文件清单、建议的领域聚类。
- 目标模块划分写入架构文档。地图本身可随时重新生成，不作为手工维护的文档。

**清理**

- 不可达且超出产品范围的代码在迁移前删除，范围以依赖地图为依据，并与已有的清理待办合并处理。
- 被功能开关关闭但仍可达的代码单独列出，由维护者逐项决定。

**注册表改为 import**

- 这是一次波及面很大的机械改动，按扩展、迁移、收缩三步进行。
- 扩展：提供方在模块作用域导出符号，注册表绑定暂时保留并指向同一实现。
- 迁移：读取方改为 import。按目录分批，顺序为基础控件与平台层、编辑能力、画布与评论与预览与导出。每批一个 ticket。
- 收缩：某个名称不再有注册表读取方后，删除其绑定；全部完成后删除注册表与安装顺序列表。
- 通过注册表注入的第三方库改为直接 import。
- 存在循环依赖或初始化顺序依赖的名称放在各批次的最后处理，先消除顺序依赖再迁移。
- 迁移尽量由脚本完成，脚本与其测试入库，供设计系统 runtime 复用。

**领域抽离**

- 领域清单的初稿：评论与批注锚点、选择与元素几何（含叠层挂载点与视口变换，即画布扩展 seam）、预览与播放、Tweaks 与组件属性、撤销历史、导出。最终清单以依赖地图为准。
- 每个领域的完成条件：实现位于自己的模块；interface 无 `any`；interface 上有测试；画布主函数通过 interface 使用它。
- 模块内部的机器变量名在抽离时改为有意义的名称。未被抽离的代码不做以改名为目的的批量修改。
- 只有一个 adapter 的地方不新增 seam。画布扩展 seam 的依据是已有的测距叠层、评论标记、选择框这三个现存使用方。

**完成标准**

- 注册表已删除；runtime 内部依赖全部通过 import 表达。
- 依赖规则由架构测试检查，覆盖 runtime 内部的领域依赖方向。
- 上述领域均满足领域完成条件。
- 画布主函数不再包含评论、测距、播放、Tweaks 的实现。
- 两个 runtime 的基线全部通过；架构文档已更新。

## Testing Decisions

- 好的测试只验证外部可观察行为：设计师看到的画面、写回的文件、发出的消息。不断言内部函数调用和状态结构。
- 最高的 seam 是"浏览器中的完整编辑器"，基线在这一层。它是规范化期间的主要回归手段。
- 领域模块在各自的 interface 上增加模块测试，沿用现有文件模块与宿主桥测试的写法和运行命令。
- 依赖方向沿用现有架构测试的方法，扩展到 runtime 内部。
- 服务响应的前后比较沿用现有的等价验证脚本；本阶段不改变后端，该脚本作为不回归的旁证。
- 迁移脚本本身有测试，输入为小型样例文件。
- 自动化、浏览器基线、宿主验收、用户验收分别报告，互不替代。

## Out of Scope

- 任何新功能或交互变化，包括评论、演示、测距、版本、Tweaks、Motion、组件库页面。
- 文件格式、路由、消息协议、文案、样式的变更。
- 后端、外壳、契约、宿主桥、存储层的重构。
- 以改名为目的、对未抽离代码的全量变量重命名。
- 为全部内部函数补全精确类型；本阶段只要求领域 interface 无 `any`。
- 与上游同步。源码独立维护，来源与许可记录不变。

## Further Notes

- 仓库中已有一项"评估并清理超出产品范围的遗留编辑器代码"的待办，本阶段的清理工作与它合并。
- 画布中注入画板页面的选择脚本是另一个大文件，它运行在画板页面内，与编辑器进程分离。它的处理方式在依赖地图完成后决定，不默认纳入领域抽离。
- 基线场景也会成为后续功能的验收基础：新功能增加新场景，旧场景保持不变。
