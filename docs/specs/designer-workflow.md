# Spec · 设计师工作流改进

记录日期：2026-11-15。状态：方向已确认，各轨道开工前补充交互细节与参考调研。前置阶段见 [runtime-modularization.md](runtime-modularization.md)，排期见 [ROADMAP.md](../../ROADMAP.md)。

## Problem Statement

MineDesign 主要由 Agent 编辑作品，但设计师仍需要像使用设计工具一样查看、核查和反馈。近期使用中的问题：

- **原型与画布的切换不顺畅。** 试用原型有"在画布播放"和"全屏播放"两个入口。进入和退出都需要选择和多次点击。
- **评论发送后不清除。** Agent 按评论修改完成后，评论仍留在列表中，设计师需要手动删除。
- **评论不能修改。** 画布上的编号点点开后无法编辑内容。
- **评论内容不在画布上。** 要在侧栏按编号查找对应文字，再回到画布对照位置。
- **没有修改历史。** 每轮修改后不能查看之前的版本，不能回退，已清除的评论也无法找回。
- **原型没有交互说明。** 交互点、状态和与后端的约定没有地方记录。设计师核查时没有依据，Agent 后续实现完整软件时还要重新听一遍说明。
- **核查间距费力。** Agent 生成的间距可能是硬编码值，没有使用设计 token。现在只能选中元素后阅读样式属性。
- **方案比较没有入口。** 想比较一个区块的几种形式时，Tweaks 只能调参数，不能切换整块方案。
- **动效不能手动调节。** 动效由 Agent 生成，设计师无法调整时间和曲线。
- **设计系统不适合走查。** 组件与说明文档的呈现方式不便于逐个检查变体、属性和使用规范；Markdown 渲染效果不理想。

## Solution

按七条轨道改进，全部建立在 runtime 规范化之后。

- **A · 评论。** 评论有明确状态：草稿、已发送、已解决。Agent 完成修改后，对应评论自动解决并从当前列表移除。评论可以二次编辑。画布上显示评论卡片，用虚线连接到目标位置。评论不分类。
- **B · 原型演示。** 一个演示入口，原型即全屏。演示界面底部显示交互说明，形式类似幻灯片的演讲者备注。设计师可以在演示中修改交互说明，也可以把修改意见作为评论发送给 Agent。
- **C · 走查测距。** 选中一个元素，按住 Alt 悬停到另一个元素或其容器，显示两者的间距。间距或尺寸没有使用设计 token 时给出标记。
- **D · 版本历史。** 每轮修改记录一条修订，形成类似提交历史的列表。可以查看某条修订、回退到它，并找回当时已解决的评论。
- **E · Tweaks 方案选择。** Agent 可以为一个区块提供多个方案。设计师在 Tweaks 中切换方案、调整参数，在页面中直接看到效果，确认后把选择发送给 Agent。
- **F · Motion。** Agent 生成的动效表达为可编辑的时间与曲线。设计师在时间轴上调整，确认后由 Agent 写回代码。
- **G · 设计系统走查。** 组件库页面：左侧目录，右侧先是总览，进入后是每个组件的变体、适用条件、属性和使用规范。说明文档的 Markdown 正确渲染。

## User Stories

评论

1. 作为设计师，我希望修改一条已写好的评论，以便补充或更正意见而不用删除重写。
2. 作为设计师，我希望在画布上直接看到评论内容，以便不用在侧栏和画布之间对照编号。
3. 作为设计师，我希望评论卡片用虚线指向目标，以便清楚它针对哪个位置。
4. 作为设计师，我希望发送后的评论显示为"已发送"，以便区分还没有发送的意见。
5. 作为设计师，我希望 Agent 修改完成后评论自动从列表移除，以便列表只包含待处理的意见。
6. 作为设计师，我希望 Agent 没有处理的评论继续保留，以便不遗漏。
7. 作为设计师，我希望能隐藏画布上的评论卡片，以便查看设计时不被遮挡。
8. 作为设计师，我希望可评论的范围清楚，以便知道元素、区域、画板哪些可以评论。

原型演示

9. 作为设计师，我希望用一个操作进入演示，以便不用在两种播放方式之间选择。
10. 作为设计师，我希望用一个操作退出演示并回到原来的画布位置，以便继续编辑。
11. 作为设计师，我希望演示时看到当前画板的交互说明，以便知道应该检查哪些行为。
12. 作为设计师，我希望在演示中修改交互说明，以便发现问题时立即更正。
13. 作为设计师，我希望把对交互说明的意见作为评论发送，以便 Agent 按它修改。
14. 作为设计师，我希望交互说明能记录与后端的约定，以便界面设计阶段就留下接口意图。
15. 作为 Agent，我希望读取作品中的交互说明，以便实现完整软件时不需要用户重新描述。
16. 作为设计师，我希望可以收起交互说明，以便只看原型本身。

走查测距

17. 作为设计师，我希望按住 Alt 悬停就看到两个元素的间距，以便像在设计工具中一样核查。
18. 作为设计师，我希望悬停到容器时看到元素到容器各边的距离，以便核查内边距。
19. 作为设计师，我希望看到间距对应的 token 名称，以便确认是否符合设计系统。
20. 作为设计师，我希望硬编码的数值被标记，以便快速发现需要修正的位置。
21. 作为设计师，我希望从测距结果直接创建评论，以便把问题交给 Agent。

版本历史

22. 作为设计师，我希望每轮 Agent 修改后有一条修订记录，以便知道改了什么。
23. 作为设计师，我希望查看某条修订时的画面，以便比较前后效果。
24. 作为设计师，我希望回退到某条修订，以便放弃不满意的修改。
25. 作为设计师，我希望修订记录关联当时的评论，以便理解修改的原因。
26. 作为设计师，我希望找回已解决的评论，以便再次发送或调整后发送。
27. 作为设计师，我希望回退本身也是一条修订，以便回退可以撤销。

Tweaks 方案选择

28. 作为设计师，我希望在 Tweaks 中切换一个区块的多个方案，以便在真实页面中比较。
29. 作为设计师，我希望切换方案时页面其他部分不变，以便只判断这一处。
30. 作为设计师，我希望确认方案后把选择和参数一起发送给 Agent，以便它清理未选方案并落实结果。
31. 作为 Agent，我希望用同一份声明提供方案与参数，以便向设计师提出可视化的选择题。

Motion

32. 作为设计师，我希望看到一个动效的时间轴，以便理解它的阶段和时长。
33. 作为设计师，我希望调整时长、延迟和曲线并立即重播，以便找到合适的手感。
34. 作为设计师，我希望确认后的参数写回作品，以便 Agent 后续修改时保留。

设计系统走查

35. 作为设计师，我希望通过目录在组件之间切换，以便逐个走查。
36. 作为设计师，我希望有一个总览页，以便了解组件库的范围。
37. 作为设计师，我希望查看每个组件的全部变体和适用条件，以便确认覆盖是否完整。
38. 作为设计师，我希望查看属性和使用规范，以便判断组件是否被正确使用。
39. 作为设计师，我希望说明文档的标题、列表、表格、代码正确显示，以便阅读规范。

## Implementation Decisions

- **批注是一个模块。** 它拥有评论的全部状态与转换：草稿、已发送、已解决。编辑、发送、解决、找回都经过它的 interface。外壳、编辑器面板、画布卡片都是它的使用方。
- **解决由 Agent 报告。** Agent 完成一轮修改后，通过工具报告已处理的评论。未报告的评论保持"已发送"。设计师始终可以手动解决或删除。
- **评论与交互说明是两种内容。** 评论是反馈，保存在本机数据中，不随作品打包。交互说明是作品内容，随作品文件保存，Agent 与导出都能读取。交互说明的修改意见可以转成评论。
- **交互说明按画板保存。** 具体格式在轨道 B 开工时确定，要求结构检查工具能校验，设计技能说明如何编写。
- **演示只保留一种方式。** "在画布播放"的入口移除；全屏演示承担原型试用。静态画板仍可全屏查看。
- **画布叠层使用画布扩展 seam。** 评论卡片、测距、演示说明都通过"选择与元素几何"领域的 interface 取得元素位置和视口变换，不修改画布主函数。
- **测距的计算从既有项目移植。** 元素配对与标注几何的计算来自作者自己的网页走查项目，按需选取，放入独立模块并带测试。
- **token 核对使用作品已安装的设计系统。** 比较对象是画板实际引用的 token；没有安装设计系统的作品只显示数值。
- **修订由存储层记录。** 每次发布形成一个内容版本；修订在此基础上保存可恢复的快照和说明，并关联当轮评论。保存位置、保留数量在轨道 D 开工时确定。回退是一次新的发布。
- **方案选择扩展现有参数声明。** 方案是参数的一种类型，沿用 Tweaks 的声明、预览与写回流程。确认后的结果作为一条结构化反馈发送。
- **Motion 沿用路线图中已定的边界。** 通用时长与曲线属于设计系统的 motion token；"哪个对象、何时触发、如何变化"属于作品。参数只保存一份。先用 Tweaks 验证闭环，再做时间轴。
- **组件库页面复用设计系统已有的组件预览与参数推断。** 是否成为独立文件类型，沿用路线图 M4 的结论。
- **各轨道开工前做参考调研。** 调研对象包括设计工具的标注、开发模式测距、演示备注、版本历史和动效编辑。调研结论写入对应 ticket，再确定交互细节。
- **界面改动遵循 DESIGN.md。** 新增的卡片、时间轴、目录等使用现有 token 与控件；需要新 token 时先更新设计约定。

## Testing Decisions

- 每个轨道在 runtime 规范化建立的浏览器基线中增加自己的场景；原有场景保持通过。
- 批注模块在 interface 上测试状态转换：编辑、发送、部分解决、全部解决、找回、作品变化后的过期判定。沿用现有服务测试的写法。
- 修订在存储层测试：记录、列出、回退、与并发保存的冲突。沿用现有文件模块测试。
- 测距计算是纯函数，用几何样例测试；移植时带上原项目的相关测试。
- 发送到聊天、Agent 报告已处理等宿主行为在对应宿主中单独验收，不以浏览器基线代替。
- 界面改动在交付时附本次构建的真实效果图。

## Out of Scope

- 评论分类、指派、多人讨论串。
- 真实后端的实现或接口联调；交互说明只记录意图。
- 持续的双向 Figma 同步；Figma 联动与 Reference 仍按路线图 M3、M5 处理。
- 云端历史、跨设备同步、分支与合并。
- 完整的动效制作工具；Motion 只覆盖 Agent 已声明的动效参数。

## Further Notes

- 推荐顺序：A → B → C → D → E → F；G 与前几项没有依赖，可在设计系统 runtime 规范化后任意时间进行。
- A 与 B 共用批注模块，D 的"找回评论"依赖 A 的状态模型，所以批注模块最先做。
- 当前 runtime 中已有一个测距叠层，轨道 C 开工时先核实它的现有行为，再决定扩展还是替换。
- 当前源码中没有 Motion 编辑模块，只有 motion token 的解析；轨道 F 是新建。
